##### 📘 REST e RESTful
**Síntese da Aula**: Esta aula aborda os conceitos fundamentais de REST (Representational State Transfer) e RESTful, destacando suas diferenças sutis e diretrizes de implementação. São discutidos os pilares do REST, como a ausência de estado (statelessness), cacheabilidade, estrutura previsível de endpoints e o uso correto dos verbos HTTP (GET, POST, PUT, PATCH, DELETE). A aula também detalha o conceito de idempotência, códigos de status HTTP mais comuns e analisa os cenários ideais para a adoção do REST em comparação com alternativas como GraphQL, WebSockets e gRPC, finalizando com exemplos práticos aplicados ao System Design.

**Conceitos Chave**:
- Diferença entre REST e RESTful
- Statelessness (Ausência de Estado)
- Cacheabilidade e Cache-Control
- Estrutura Previsível e Verbos HTTP
- Mapeamento Prático de Endpoints
- Idempotência de Métodos HTTP
- Códigos de Status HTTP
- Quando usar REST vs. Outros Protocolos (GraphQL, WebSockets, gRPC)
- Exemplos Práticos em System Design

**Linha do Tempo & Tópicos Práticos**:
- **[00:00 - 01:15]**: Introdução aos termos REST e RESTful, que frequentemente são usados de forma intercambiável. O instrutor explica que REST (Representational State Transfer) é um conjunto de restrições arquiteturais, enquanto RESTful refere-se a um sistema que implementa essas regras à risca. Na prática, muitas empresas tentam criar APIs RESTful, mas nem sempre seguem todas as regras estritamente, o que é aceitável e comum no mercado.
- **[01:15 - 02:33]**: Explicação detalhada sobre o conceito de Statelessness (ausência de estado). Em uma arquitetura REST, cada requisição do cliente para o servidor deve conter todas as informações necessárias para que o servidor entenda e processe a requisição. O servidor não deve armazenar o contexto da sessão do cliente. Por exemplo, ao criar um comentário em uma rede social, a requisição POST deve conter o token de autenticação, o ID do usuário, o texto do comentário e quaisquer metadados necessários, sem depender de um estado previamente salvo no servidor.
- **[02:33 - 03:16]**: Discussão sobre cacheabilidade em REST. O uso de cabeçalhos como Cache-Control permite que as respostas sejam armazenadas em cache por intermediários ou pelo próprio cliente, melhorando a escalabilidade do sistema. O instrutor exemplifica o uso de 'Cache-Control: max-age=3600' para indicar que a resposta pode ser cacheada por 1 hora (3600 segundos).
- **[03:16 - 05:13]**: A importância de uma estrutura previsível de endpoints e o uso correto dos verbos HTTP. O instrutor apresenta um anti-padrão comum: usar o método GET para criar recursos passando parâmetros na URL (ex: GET /create-comment?comment=texto). Em REST, os verbos HTTP devem ditar a ação, e os caminhos (URIs) devem representar os recursos (substantivos).
- **[05:13 - 07:08]**: Mapeamento prático de endpoints usando o recurso '/comments' como exemplo. São explicados os comportamentos esperados para cada verbo HTTP:
- GET /comments: Retorna uma lista de comentários.
- GET /comments/123: Retorna o comentário específico de ID 123.
- POST /comments: Cria um novo comentário.
- PUT /comments/123: Atualiza por completo o comentário 123 (substituição de entidade).
- PATCH /comments/123: Atualiza parcialmente o comentário 123 (ex: apenas o texto).
- DELETE /comments/123: Remove o comentário 123.
- **[07:08 - 08:45]**: Diferenciação prática entre REST e RESTful. Uma API RESTful evita expor verbos ou intenções no caminho da URL (ex: /get-user ou /create-user). O correto é expor apenas o recurso (/users) e usar o método HTTP correspondente (GET ou POST). Embora expor verbos na URL seja um desvio do padrão RESTful, o instrutor pontua que, se estiver bem documentado, ainda é compreensível, mas deve ser evitado.
- **[08:45 - 11:42]**: Explicação sobre Idempotência. Um método é considerado idempotente se múltiplas requisições idênticas produzem o mesmo resultado de estado no servidor. GET, PUT e DELETE são idempotentes. POST não é idempotente (múltiplos POSTs criam múltiplos recursos). O instrutor discute um caso limítrofe: se um GET em um comentário também incrementa um contador de visualizações no banco de dados, estritamente falando, ele deixa de ser idempotente porque altera o estado do servidor. Contudo, na prática, esse comportamento é amplamente aceito.
- **[11:42 - 13:54]**: Apresentação dos códigos de status HTTP mais importantes para APIs RESTful:
- 200 OK: Sucesso padrão para requisições GET, PUT, PATCH.
- 201 Created: Sucesso para criação de recursos (POST).
- 400 Bad Request: Erro do cliente (requisição malformada).
- 401 Unauthorized / 403 Forbidden: Problemas de autenticação e permissão.
- 404 Not Found: Recurso ou endpoint não encontrado.
- 500 Internal Server Error: Erro inesperado no servidor (bug).

**Linha do Tempo & Tópicos Práticos**:
- **[00:00 - 01:44]**: O instrutor introduz o conceito de protocolos em tempo real (real-time), explicando a necessidade de sincronia entre cliente e servidor. - **[01:44 - 03:15]**: Explicação sobre as limitações do modelo HTTP tradicional (Request-Response) para tempo real. É apresentado o conceito de Short Polling, onde o cliente faz requisições repetidas ao servidor em intervalos curtos (ex: a cada 1 segundo) perguntando se há atualizações. O instrutor aponta o problema de sobrecarga do servidor caso muitos clientes adotem essa abordagem e usa o exemplo de um jogo de xadrez online.
- **[03:15 - 04:15]**: Apresentação do Long Polling. Diferente do Short Polling, o cliente envia uma requisição e o servidor mantém a conexão aberta até que novos dados estejam disponíveis ou ocorra um timeout (geralmente de 30 segundos a 1 minuto). - **[04:15 - 05:32]**: Explicação sobre WebSockets. O protocolo inicia com um handshake HTTP padrão e depois realiza um upgrade para uma conexão bidirecional e persistente sobre TCP. Cliente e servidor podem enviar mensagens a qualquer momento, em qualquer ordem, através do mesmo canal aberto. O instrutor menciona a complexidade de escalabilidade horizontal e o uso de Load Balancers com WebSockets.
- **[05:32 - 06:16]**: Introdução aos Server-Sent Events (SSE). Neste modelo unidirecional, o cliente estabelece uma conexão e o servidor continuamente faz o 'push' de atualizações para o cliente. - **[06:16 - 09:18]**: Mapeamento prático de qual protocolo utilizar para cada cenário. Para chats (ex: WhatsApp, ChatGPT), WebSockets são os mais recomendados. Para notificações, SSE é a primeira escolha (com Long Polling como alternativa). Para atualizações pontuais de estado (ex: foto processada), Long Polling é muito adequado. Para consumo de APIs de terceiros ou sistemas legados onde não se controla o servidor, o Short Polling é a única alternativa viável respeitando os limites de taxa (rate limits).

##### 📘 BFF - Backend for Frontend
