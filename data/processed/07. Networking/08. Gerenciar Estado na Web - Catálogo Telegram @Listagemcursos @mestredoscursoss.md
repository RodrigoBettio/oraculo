# Gerenciamento de Estado na Web

## Resumo Geral
Nesta aula do módulo de **Networking**, é discutido o desafio de gerenciar estados em uma arquitetura web baseada no protocolo HTTP, que por padrão é *stateless* (não mantém estado entre requisições). Para que aplicações modernas funcionem (como e-commerces e fluxos de checkout), foram criadas estratégias para persistir o contexto do usuário. Foram detalhadas as abordagens de **Sessões baseadas em servidor (com Redis/DB)**, **Cookies** e **JSON Web Tokens (JWT)**.

---

## Principais Tópicos Abordados

### 1. O Problema do HTTP Stateless
* O HTTP não guarda memória de requisições anteriores.
* Exemplo prático: Um fluxo de compra de passagens aéreas em 4 etapas (Filtros -> Dados Pessoais -> Serviços Adicionais -> Pagamento). Sem um mecanismo de estado, a tela de pagamento não saberia quem é o comprador ou qual passagem está sendo adquirida.

### 2. Sessões e Session ID
* **Fluxo**: O usuário se autentica, o servidor gera um identificador único (`Session ID`) e o envia ao cliente.
* O cliente anexa esse `Session ID` a cada nova requisição.
* **Armazenamento de Sessão**:
  * *In-Memory (Servidor)*: Não escala. Se houver múltiplos servidores atrás de um balanceador de carga, a sessão se perde se o usuário for direcionado a outra máquina.
  * *Banco de Dados / Redis*: Solução ideal para escalabilidade horizontal. O Redis, por ser um banco chave-valor em memória, oferece altíssima velocidade para leitura e escrita de dados de sessão.

### 3. Cookies
* Pequenos arquivos de texto gravados no navegador do cliente.
* Podem guardar estados simples (como preferências de tema ou progresso de jogos web).
* Se limpos pelo usuário, o estado associado é completamente perdido.

### 4. JSON Web Tokens (JWT)
* Uma alternativa descentralizada às sessões tradicionais.
* O servidor gera um token assinado digitalmente contendo um *payload* (ex: `user_id`, data de expiração `exp`).
* O cliente armazena esse token e o envia no cabeçalho das requisições.
* **Vantagem**: O servidor não precisa consultar um banco de dados de sessões a cada requisição; basta validar a assinatura do token.
* **Segurança**: Deve ser transmitido estritamente via HTTPS para evitar interceptações (*sniffing*/*spoofing*).

---

## Comparativo de Soluções de Estado

| Mecanismo | Onde é armazenado | Escalabilidade | Segurança | Uso Comum |
| :--- | :--- | :--- | :--- | :--- |
| **Session (In-Memory)** | Memória do Servidor Web | Baixa (Não escala) | Alta | Aplicações pequenas/monolíticas |
| **Session (Redis/DB)** | Banco de Dados Centralizado | Alta | Alta | E-commerces, Sistemas Financeiros |
| **JWT** | Lado do Cliente (Browser/App) | Excelente (Stateless) | Média (Requer HTTPS) | APIs RESTful, Microserviços |
| **Cookies** | Navegador do Cliente | Alta | Média | Preferências, rastreamento, estados simples |
