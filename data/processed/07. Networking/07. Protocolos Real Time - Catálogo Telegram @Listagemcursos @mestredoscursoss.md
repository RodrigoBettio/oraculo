# Protocolos Real-time

## Resumo Geral
Em sistemas web modernos, há uma necessidade crescente de comunicação em tempo real (real-time) para garantir a sincronia de dados entre clientes e servidores. Esta aula analisa as quatro principais abordagens para implementar essa funcionalidade, comparando suas características técnicas, vantagens, desvantagens e casos de uso ideais.

---

## Abordagens de Comunicação Real-time

### 1. Short Polling
* **Funcionamento**: O cliente envia requisições HTTP repetidas ao servidor em intervalos de tempo estritos e predefinidos (ex: a cada 1 ou 2 segundos) perguntando por novas atualizações.
* **Vantagens**: Extremamente simples de implementar. Pode ser feito de forma unilateral pelo cliente, sem necessidade de suporte especial ou alterações na infraestrutura do servidor.
* **Desvantagens**: Alta latência e desperdício massivo de recursos (processamento e banda), pois a maioria das requisições retornará vazia. Pode facilmente sobrecarregar o servidor se houver muitos clientes ativos.
* **Caso de Uso Ideal**: Integração com APIs de terceiros ou sistemas legados onde não se tem controle sobre o código do servidor, utilizando a técnica respeitando os limites de requisição (*rate limits*).

### 2. Long Polling
* **Funcionamento**: O cliente faz uma requisição HTTP e o servidor segura a resposta (mantém a conexão aberta) até que haja uma nova informação para enviar ou ocorra um *timeout* (geralmente entre 30 e 60 segundos). Assim que o cliente recebe a resposta, ele abre imediatamente uma nova requisição.
* **Vantagens**: Latência muito menor que o Short Polling e menor desperdício de requisições vazias.
* **Desvantagens**: Exige que o servidor gerencie e mantenha múltiplas conexões abertas simultaneamente, o que consome memória e recursos de rede.
* **Caso de Uso Ideal**: Atualizações de estado pontuais e transições únicas (ex: aguardar o processamento de uma imagem ou a geração de um relatório).

### 3. WebSockets
* **Funcionamento**: A conexão inicia com um handshake HTTP padrão e é atualizada (*upgrade*) para um canal de comunicação bidirecional, persistente e de baixa latência sobre TCP. Tanto o cliente quanto o servidor podem enviar dados a qualquer momento de forma assíncrona.
* **Vantagens**: Comunicação bidirecional real com overhead mínimo após o estabelecimento da conexão.
* **Desvantagens**: Complexidade de implementação e dificuldades para escalar horizontalmente (exige gerenciamento de estado de conexões ativas entre múltiplos servidores e suporte adequado em Load Balancers).
* **Caso de Uso Ideal**: Aplicações altamente interativas e bidirecionais, como chats (WhatsApp, Slack), jogos multiplayer online e ferramentas colaborativas em tempo real.

### 4. Server-Sent Events (SSE)
* **Funcionamento**: O cliente abre uma conexão HTTP persistente e o servidor envia atualizações de forma unidirecional (apenas do servidor para o cliente) à medida que novos eventos ocorrem.
* **Vantagens**: Mais simples de implementar do que WebSockets para fluxos unidirecionais; reconexão automática nativa.
* **Desvantagens**: Unidirecional (o cliente não pode enviar dados de volta pelo mesmo canal) e menor compatibilidade histórica em navegadores muito antigos.
* **Caso de Uso Ideal**: Feeds de dados ao vivo (cotações de ações, placares esportivos) e sistemas de notificações push.

---

## Matriz de Decisão de Protocolos

| Cenário de Uso | Protocolo Recomendado | Justificativa |
| :--- | :--- | :--- |
| **Sistemas de Chat / LLMs** | WebSockets | Exige troca constante e bidirecional de mensagens com baixíssima latência. |
| **Notificações Push** | Server-Sent Events (SSE) | O fluxo de dados é estritamente do servidor para o cliente. Long Polling serve como alternativa. |
| **Atualizações de Estado Único** | Long Polling | Ideal para esperar uma resposta de um processo demorado (ex: upload/conversão de arquivo) que ocorre uma única vez. |
| **APIs de Terceiros / Legados** | Short Polling | Única opção viável quando não se tem controle sobre o servidor para implementar protocolos persistentes. |
