# REST e RESTful

## Resumo
Esta aula aborda de forma aprofundada os conceitos de **REST (Representational State Transfer)** e **RESTful**, desmistificando a ideia de que são termos idênticos. Enquanto o REST representa o conjunto de princípios e restrições arquiteturais definidos para a web, o termo RESTful é atribuído aos sistemas que implementam rigorosamente essas regras.

Durante a aula, são detalhados os pilares fundamentais para a construção de APIs modernas:
1. **Statelessness (Ausência de Estado):** Cada requisição deve ser autossuficiente, contendo todas as credenciais, tokens e dados necessários para o processamento, sem depender de sessões mantidas no servidor.
2. **Cacheabilidade:** O uso correto de cabeçalhos como `Cache-Control` para otimizar a performance e a escalabilidade.
3. **Verbos HTTP Semânticos:** A utilização correta de `GET`, `POST`, `PUT`, `PATCH` e `DELETE` mapeados para substantivos que representam recursos (ex: `/comments`), evitando anti-padrões como colocar verbos no caminho da URL (ex: `/create-user`).
4. **Idempotência:** A garantia de que requisições repetidas (como `PUT` ou `DELETE`) não gerem efeitos colaterais inesperados no servidor.
5. **Códigos de Status HTTP:** A semântica de respostas como `200 OK`, `201 Created`, `400 Bad Request`, `404 Not Found` e `500 Internal Server Error`.

Por fim, a aula contextualiza o uso do REST em cenários reais de **System Design** (como encurtadores de URL e redes sociais) e discute quando optar por alternativas como **GraphQL**, **WebSockets** ou **gRPC**.

## Códigos e Mapeamentos de Endpoints

### Mapeamento Padrão de Recursos (`/comments`)
Uma API RESTful deve utilizar substantivos no plural para identificar recursos e os métodos HTTP para definir as ações:

```http
GET /comments          -> Lista todos os comentários
GET /comments/123      -> Obtém o comentário com ID 123
POST /comments         -> Cria um novo comentário
PUT /comments/123      -> Substitui completamente o comentário 123
PATCH /comments/123    -> Atualiza parcialmente o comentário 123
DELETE /comments/123   -> Remove o comentário 123
```

### Anti-padrões vs. Padrão RESTful
Evite expor ações ou verbos diretamente no caminho da URL:

```http
// Anti-padrões (Evitar)
GET /get-user
POST /create-user
GET /create-comment?comment=texto

// Padrão RESTful (Recomendado)
GET /users
POST /users
POST /comments
```

### Exemplo de Requisição Stateless (POST)
Toda a informação necessária para processar a criação do recurso é enviada no corpo e nos cabeçalhos da requisição:

```http
POST /comments HTTP/1.1
Host: api.redesocial.com
Authorization: Bearer <token_de_autenticacao>
Content-Type: application/json

{
  "user_id": "12345",
  "video_id": "67890",
  "text": "Este é um comentário de exemplo."
}
```

### Exemplo de Resposta com Cache
```http
HTTP/1.1 200 OK
Cache-Control: max-age=3600
Content-Type: application/json

{
  "data": "Informação cacheável por 1 hora"
}
```

### Exemplo de System Design: Encurtador de URL
```http
POST /short-links HTTP/1.1
Host: api.encurtador.com
Content-Type: application/json

{
  "long_url": "https://www.exemplo-longo-de-site.com/artigo/detalhes"
}
```

## Quando NÃO usar REST
Embora o REST seja o padrão da indústria para a maioria das aplicações web (cobrindo cerca de 80% dos casos de uso), ele apresenta limitações em cenários específicos:
- **Consultas Complexas/Aninhadas:** Se o cliente precisa de dados muito customizados e aninhados, REST pode sofrer de *over-fetching* ou *under-fetching*. Nesses casos, **GraphQL** é mais indicado.
- **Tempo Real (Real-time):** Para chats, dashboards financeiros ou jogos multiplayer, requisições HTTP tradicionais são ineficientes. Recomenda-se o uso de **WebSockets**.
- **Comunicação entre Microsserviços:** Para comunicação interna de alta performance e baixa latência, o **gRPC (RPC)** é preferível devido à serialização binária eficiente (Protocol Buffers).
